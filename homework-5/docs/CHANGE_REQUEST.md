# Change Request — CAMPUS-102

- **Релиз:** v1.9.0
- **Модуль:** Бронирование аудиторий
- **Изменение:** `Auditories.Capacity`: `smallint` → `integer`.

## Бизнес-цель
Расширить диапазон вместимости аудитории. PostgreSQL `smallint` ограничен значением 32767, `integer` поддерживает существенно больший диапазон. Отрицательные значения запрещаются на уровне приложения.

## Maintenance Window
Вторник, 02:00–03:00 по локальному времени кампуса. Это предполагаемое окно минимальной активности; перед релизом его необходимо подтвердить по метрикам трафика и расписанию занятий. Expand/Migrate выполняются без плановой остановки сервиса.

## План релиза
1. Создать и проверить резервную копию.
2. Выполнить `01_expand.sql`.
3. Развернуть совместимую версию приложения с dual-write.
4. Выполнить `02_migrate.sql`, проверить совпадение значений.
5. Переключить чтение на `CapacityInt`, обновить все экземпляры и фоновые процессы.
6. После периода наблюдения выполнить `03_contract.sql`.
7. Проверить бронирование, логи, трассировки и метрики.

## Откат
До Contract: `kubectl rollout undo deployment/auditory-booking-api -n campus`. Старая колонка сохранена, поэтому предыдущая версия совместима. Новую колонку можно оставить до отдельного удаления.

После Contract одного `rollout undo` недостаточно. Нужна компенсирующая миграция: добавить `CapacityLegacy smallint`, проверить диапазон, скопировать данные и развернуть совместимую версию. Если значения выше `32767`, автоматическое обратное преобразование с потерей данных запрещено. Проверить откат командой `kubectl rollout status deployment/auditory-booking-api -n campus`.

## Риски
- Старые клиенты: старая колонка сохраняется до Contract.
- Расхождение данных: dual-write в одной транзакции и SQL-сверка.
- Длительный UPDATE: на больших таблицах выполнять пакетами.
- Несовместимый Contract: выполнять только после подтверждения обновления всех потребителей.
